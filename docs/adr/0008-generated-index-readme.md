## Context

`issues/README.md` listing the issues ("preview the issues") is exactly the
kind of data Principle 3 forbids storing: it is derived (titles, statuses,
counts) and it goes stale. §2 says a principle may yield, but only when three
things hold, and only **in writing** — this is that writing.

The push for it is real: with content at the tree root (ADR 0005) and
`README.md` bodies (ADR 0006), a forge browse is *one* page away from a usable
read-only board — except the listing page itself, which shows raw folder names.
The pilot repo demonstrates the cost of not having it: there is no way to see
"what's in progress" without cloning and running `dit`.

The §2 yield test, applied honestly:

1. **Cost measurable and large?** Yes — the raw repo is unbrowsable as a board;
   every non-clone reader (manager, stakeholder, future contributor on the
   forge) is locked out of the data.
2. **Benefit speculative or rare?** The principle's benefit here — keeping the
   source of truth free of derived state — is real but fully preserved by the
   containment below; what it protects against does not occur for a file the
   indexer refuses to read.
3. **Contained and reversible?** Yes — see Decision. Deleting every generated
   index loses zero data; the file format itself is untouched.

## Options considered

| Option | Cost | Consequence |
|---|---|---|
| No index; static root README only (status quo) | Forge browsing dead-ends at folder soup | Principle intact, product worse |
| CLI writes the index as a side effect of every write | Violates Principle 3 outright — local staleness *lies*, write path grows a second concern | Rejected |
| **CI/dit-bot regenerates on push** | One derived file class in the tree; stale between pushes | **Chosen** |

## Decision

A generation command (working name `dit docs build --index`) emits
`issues/README.md` — issues grouped by status, ordered by `number` (ADR 0007),
linking each entry to its folder. Per-shard READMEs (`issues/2026/README.md`)
may follow the same pattern later.

Containment rules — these are the whole decision:

- **Regenerated, never edited.** The file starts with
  `<!-- generated by dit <version> — do not edit; run dit docs build --index -->`.
  Hand edits are overwritten without warning.
- **CI is the only writer.** The local CLI never writes it as a side effect of
  issue writes. Solo users regenerate on demand or via a `pre-push` hook recipe.
- **An output, never an input.** The indexer **skips** generated index files —
  they are not issues, not doc pages, and never feed DQL. Source of truth is
  unchanged; a publication artifact happens to live in the same tree, like a
  lockfile.
- **Staleness is visible.** `dit validate` regenerates in memory and warns on
  a diff.

## Consequences

- Principle 3 yields for exactly this file class, recorded here; widening the
  class (per-issue generated files, badges, counters) requires a new ADR.
- Diff noise: one file changes per push that touches issues. Accepted.
- The root `README.md` written by `dit init` stays hand-editable and separate —
  it may *link into* the generated index but is never itself generated.

## Verification

Nothing git-specific to run — the claims are about our own tooling. The two
properties to test when implemented (TDD, `dit-store`/`dit-index` suites): the
indexer skips a file carrying the generated marker, and regeneration from an
unchanged repo is byte-identical (determinism — otherwise CI commits churn).
